### Full product specification field mapping

`ProductLine`, `JOSpecs`, `JOTemplateData` and finished-good specs map to `product_specifications`:

- Type/name; `od1`, `od2`, `id1`, `id2`, height, overall height; length, width, thickness, depth, pocket count; diameter; cloth cutting width/length; spring plate center-to-center, width and length; pad OD/ID.
- Media, inner core, outer core, O-ring, gasket, end cap, OEM part number, brand, filtration rating, others and notes. Quantity belongs to the order item/JO, not the specification.
- Dimension input is currently text, including legacy mixed-unit descriptions. Draft VARCHAR columns preserve it; numeric dimensions/units/tolerances require confirmation. Group dimension/required-part rules remain the code-defined `GROUP_TEMPLATES` in `store/filterTemplates.ts` until a configurable catalogue is requested.

### Observed validation (must be repeated on server)

- Client registration: company/contact/email/username/password required; basic email pattern; case-insensitive account/pending-application company/email/username duplicate check. Phone is captured but not required. Registration currently does not impose the employee password minimum.
- Employees: employee ID/name/department/job title/email/username/allowed staff role required; valid email; initial/reset password at least 8 characters; duplicate email/username/employee ID blocked. Client account edits require company, valid email and username. Client password change needs current password, new password >=8 and matching confirmation.
- Client wizard: type and filter name >=3 characters; first group dimension and media required at wizard step 2; rating selection/default; integer quantity >=10 per product. Final submit checks contact and quantities but does not uniformly repeat all earlier step checks. Sales new inquiry checks name/contact/filter name>=3, MOQ 10, rush date when urgent, but its quantity check is weaker than client integer validation.
- Quotation send: at least one described line, quantity >0, unit price >=0; delivery method/place required; shortage requires a lead time selection. Discounts bounded to 0–100; downpayment/VAT/costing values must be validated and recalculated by backend. Existing quote line quantities may be below inquiry MOQ, so SQL enforces >0 there and >=10 only on inquiry items.
- Materials: name required; finite nonnegative price/stock/threshold. Stock requests need an existing inquiry and valid BOM requirements. JO generation validates stock before deduction; production due date must be a valid ISO date and is read-only after issuance. All nine stages must be completed; paused jobs cannot advance; revert/cancel reasons are required.
- Payments: attached proof, amount >0 and no greater than current submission allowance; verified rather than pending amounts determine clearance. Current verification action can accept an override amount without equivalent robust bounds. API must lock/recompute balance before accepting or verifying payments and require an accounting actor.
- Revision request text >=5 characters; cancellation reason required; notification reply >=3 characters. Files generally advertise PDF/JPG/JPEG/PNG extensions; signed DR store validates a PDF/JPEG/PNG data URL prefix. No consistent maximum file size, authoritative content sniffing, or malware handling is implemented. Browser `accept` is not server validation.

## Relationships, workflows and transaction boundaries

1. Client/user submits order with client-owned product specification rows and files. Composite FKs bind item/specification/JO/finished-good client scope and quotation/stock-response order scope. Staff drafts per-product BOM/costing and quotation revision. Warehouse responses are versioned snapshots, not live reservations. A quotation number is owned by one order through quotation_references and can be reused across its revisions. Sent revisions retain frozen prices/names/units and line descriptions.
2. Client submits PO against the selected quotation revision; Sales receives it. Issue one or more product-specific JOs under the same order. Replacement JOs explicitly link a request; reorders create a new order referencing the source, with new transaction documents.
3. JO issuance must lock counter/material rows in deterministic order, recompute aggregate material needs, validate available balances, copy specification/BOM snapshots, insert JOs, record idempotent material deductions and update balances in one transaction. Waste% is informational in current costing, not an automatic extra deduction. Cancellation/restoration must use compensating movements once, never delete history. No automatic per-station material deductions are inferred.
4. Production events and stage cursor update atomically, with authenticated actor and reason where required. Completion cursor 9 is separate from the nine real stages (0–8). Lock job before advancing/reverting; check all stage completions before finish. Enforce immutable due date/snapshots in service rules, not an unrestricted edit endpoint.
5. Shipment has waybill and DR. Warehouse print/handoff, Accounting DR generation/send-to-logistics, Logistics dispatch/signed receipt/delivery are separate events. Composite FKs carry the same order through job/shipment/DR/signed-copy/invoice evidence. Lock DR while staging/discarding/accepting a signed copy and verify available file and authorization. The checked accepted_slot plus unique key enforces at most one accepted copy per DR; invoice evidence may reference only same-order slot=1 copies. Due-date basis selection still needs an approved split-billing policy.
6. Invoice draft and explicit send are separate. Pre-invoice downpayments attach to order; invoice-linked payments must belong to that order (composite FK). Lock order/invoice and pending payment rows while computing remaining allowance or verification; prevent concurrent overpayment including pending submissions. Payments are canonical; derive collected amounts, outstanding, paid/overdue/downpayment state. Do not sum legacy receipts and confirmedPayments again.
7. Pending registration uniqueness spans accounts and applications; one serialized server registration/approval workflow must recheck both and rely on final user uniqueness. Normalize identity input; do not let rejected applications permanently reserve an identity. Seed only module grants; classify each future endpoint's read/write authority before implementing.

## Missing requirements / discrepancies requiring decisions

| Issue | Evidence and draft treatment |
| --- | --- |
| Branch name | Workspace `dev-phase`; requested `development-phase`. Files stay in current checkout for review; no branch mutation |
| COD versus terms | Flowcharts explicitly distinguish new/COD downpayment and terms; current `paymentTerms` union only 15/30-Day Terms and quotation-set DP%. Seed NET15/NET30 only; clarify COD choice, DP requirement and release gate before coding policy |
| Due-date event | Corrected on re-review: although generateInvoice/markDelivered use legacy `clientSignedDRUploadedAt`, the effect in `orders.tsx` around lines 961–992 clears invalid receipt-derived state and recalculates cycle/due dates from valid `signedDeliveryReceiptReceivedAt`; Logistics uses that newer timestamp too. This is effective single-record behavior. Approve its backend authority, split-delivery first/last/per-invoice basis, calendar boundary and invoice-before/after-receipt/reset rules. Draft constrains accepted evidence but does not compute due dates |
| Split JOs versus billing | `finalizeProductJOs` clones Inquiry rows; pricing/documents may be copied between parent/children. Confirm whether PO/invoice/DR/payment belong per inquiry or per JO, and first/last receipt used for multiple deliveries. Draft: one PO/invoice per order, multiple JOs, one shipment/DR per JO. This cardinality needs approval before migration |
| Production stages / authority | Current code has 9 stages plus completed cursor; historical QA says 10. Flowchart says owner updates and one item/station; current owner lacks production access. Draft seeds current 9, does not enforce station capacity or grant owner new rights |
| Inventory deduction | Flowcharts describe no automatic per-stage measurement; current source deducts BOM at JO generation and restores on cancellation. Draft supports issuance-time atomic movements; confirm this intended behavior and opening balances |
| Thresholds and procurement | Notes show fixed imported-media schedules and supplier order actions; current material model has configurable thresholds/free-text supplier, no purchasing workflow. Do not infer supplier POs, purchase approvals, stock reservations or procurement schedules. These need separate requirements |
| Replacement policy | Store has replacement requests/JO actions and a comment about maximum 2; client quote terms state no replacements after delivery. Draft optional request/proof/JO links preserve the source workflow but no eligibility/max-2 rule is enforced until confirmed |
| Client identity | Accounts, `CLIENTS_DATA`, portal settings and orders use different name-based identities. Draft IDs unify them; review duplicates/renames and single/multiple contacts/accounts before importing data |
| Specification units and keys | Free-text dimensions, legacy human filter type strings, OEM/Enter-Fil PN usage vary; establish unit normalization, tolerances, PN uniqueness and catalogue mappings. No fuzzy matches automatically imported |
| Quote and document immutability | Confirm version-number/reference format, discount ordering, VAT rounding, packaging/shipping allocation and historical company/client letterhead snapshots. Draft preserves commercial values but does not freeze every company profile field automatically; retain rendered document objects for exact historical copies |
| Security/workflow details | Confirm endpoint write permissions, server session/reset/invite strategy, audit/retention rules and initial admin onboarding. UI notes mention email invitations; actual email delivery service is absent. No password emails/invite system inferred |
| File controls | Confirm size limits, malware scanning, retention/deletion, allowed sketch formats and who may accept signed DR. Define separate dev/prod buckets/project/region later; no credentials or resources created |
| Registration/rules gaps | Agree common password policy and pending identity serialization. Confirm whether any JO/replacement may fall below MOQ; draft allows JO qty>0, inquiry qty>=10. Client company-name uniqueness reflects current duplicate checks but needs review for separate branches of one company |
| Financial/report semantics | Agree payment verification overrides, adjustments/refunds (not implemented), invoice correction/cancellation and revenue basis (invoiced vs verified collections). Backend must avoid double-counting order totals across split JOs and keep report definitions explicit |

No uncertain rule above has been silently promoted to a trigger or automatic approval policy. Resolve the relevant issues before applying or building APIs on this draft.
