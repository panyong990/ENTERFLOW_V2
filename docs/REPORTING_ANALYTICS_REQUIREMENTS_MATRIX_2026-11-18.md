## Data/security conclusions and implementation decision

1. **Stabilize the existing reporting scope before adding metrics.** The PDFs are now reviewed and require preservation of reporting, not invented detailed KPI definitions. Reconcile current fields/formulas/date semantics/freshness and confidential visibility with integrated MAIN and approved policy. Do not add an endpoint merely because a source formula exists or a route is disconnected.
2. **Do not connect Owner analytics to Sales-only routes.** `GET /api/sales/dashboard` is role-gated to Sales. The owner/operations `reports:read` grants do not override the router's role check.
3. **Reuse only existing authorized data sources after definition approval.** Inventory is available to Owner/Operations through `inventory:read`; JO data is available through the scoped Production API. Neither source supplies the entire pipeline, invoice/collection, delivery, or history dataset.
4. **Preserve unavailable states for disconnected reporting.** KPICard already hides calculated Real Mode values; the previous displayed-zero finding was incorrect. The Operations bottleneck panel now also withholds unsupported issue/resolution results instead of treating catalog placeholders or incomplete stores as operational evidence. Owner analytics retains unavailable values and disabled exports.
5. **Resolve the Operations inventory-alert ambiguity.** The visible label defines low/out-of-stock, but implementation also counts `unavailable`. Unknown quantity is distinct from verified zero; do not silently classify unknown as low/out-of-stock. A narrowly scoped correction can be assessed separately against the existing inventory acceptance rule.
6. **Review data minimization before expanding APIs.** Inventory reads currently include unit price and supplier for every role granted inventory read. Production Job Order reads include client names and product specifications for Owner/Operations. Existing route permissions are explicit; whether those fields are appropriate for report output still needs policy confirmation.
7. **No schema change is indicated.** The blocker is requirements, source coverage, semantics, and role policy—not a missing database object. No live database or browser verification was performed.

## Acceptance evidence required

- Use the reviewed handoff pages as scope authority. Where they do not define details, reconcile existing reports against integrated MAIN/approved business definitions: formula, numerator/denominator, stages, archived/cancelled handling, date/timezone, as-of/period, rounding, unknown/null and missing-data display. Preserve existing approved behavior; do not invent formulas or treat source observations as approvals.
- Role matrix explicitly stating whether Owner and Operations may see financial totals, client-level revenue, supplier/unit-cost fields, cancellation reasons, and detailed product specifications.
- Source-to-field map and freshness/refresh expectation, identifying authoritative tables/API contracts and whether data is paginated or event-sourced.
- Unit tests for formulas/date boundaries/nulls; HTTP tests for role denial, permission denial, data minimization, and tenant/ownership boundaries; then authorized browser and persistence verification.

Until these are supplied, reporting status remains **In progress**; no Owner/Operations reporting workflow is accepted.
